# Atlas — Multimodal Agentic Research System

[![CI](https://github.com/mengchen-atx/PaperResearch-RL/actions/workflows/ci.yml/badge.svg)](https://github.com/mengchen-atx/PaperResearch-RL/actions/workflows/ci.yml)

Atlas answers research questions over document collections (PDFs, text, tables, charts). It plans, retrieves,
calls tools, checks whether it has enough evidence, iterates, and writes a report with page-level citations that
are checked against the sources. It also closes the loop for model improvement: every agent run becomes a
trajectory, and those trajectories feed supervised fine-tuning (LoRA/QLoRA) and an agentic-RL environment. All of
it is measured with a verified benchmark.

> **Honesty contract.** Every number in this README is generated by a command in this repo and stored under
> `benchmarks/results/` or `data/processed/`. What ran versus what is only configured is listed in
> [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md). No vLLM, Kubernetes, or QLoRA numbers are claimed, because
> no NVIDIA GPU or cluster was available.

---

## Why this project exists

LLMs answer research questions fluently but unreliably. They misremember numbers, cannot show sources, and fail on
facts that live in tables or charts. Atlas is a working, measured answer to these engineering questions:

1. How much does retrieval help, and which retrieval components (BM25, dense, fusion, reranking) matter?
2. When does a multi-step agent beat single-shot RAG, and what does it cost in tool calls and latency?
3. Can a small open model learn the agent protocol from its own successful trajectories (SFT)?
4. Can RL make tool use more efficient without losing accuracy?
5. What does it take to serve this reliably: async jobs, streaming, caching, vLLM, horizontal scaling?

## Headline results (measured, 46-question verified benchmark, Apple M4)

| System (same benchmark, same prompts) | Answer accuracy (95% CI) | Tool calls | p50 latency |
|---|---|---|---|
| Closed-book Qwen2.5-1.5B (no retrieval) | 10.9% (2.2–19.6) | – | 1.4 s |
| Extractive answerer, no LLM (retrieval floor) | 41.3% (28.3–54.3) | – | 0.17 s |
| Vanilla RAG (dense top-5) | 63.0% (50.0–76.1) | – | 9.5 s |
| Hybrid RAG (BM25 + dense, RRF) | 58.7% (43.5–71.7) | – | 5.4 s |
| **Hybrid + cross-encoder rerank RAG** | **69.6%** (56.5–82.6) | – | 5.3 s |
| Agent, text-only tools | 67.4% (54.3–80.4) | 1.93 | 11.5 s |
| Agent, heuristic router, all tools | 67.4% (52.2–80.4) | 2.70 | 19.6 s |
| Agent, LLM router | 69.6% (56.5–82.6) | 5.52 | 31.2 s |
| Agent, RL-learned router | 67.4% (54.3–80.4) | 1.00 | 9.2 s |
| Agent, fixed single-search baseline (no RL) | 67.4% (54.3–80.4) | 1.00 | 8.6 s |

| Component | Measured result |
|---|---|
| Retrieval Recall@5 | dense 81.5 → BM25 85.9 → hybrid 87.0 → hybrid + rerank 88.0 |
| Agentic RL (13 held-out questions, same env) | learned router matches the heuristic's success (46.2%) with 1.00 vs 1.69 tool calls (one search per episode, see below); random policy 30.8% |
| SFT, LoRA on Qwen2.5-0.5B (31 held-out router steps) | valid JSON 71.0% → 100%, correct action 45.2% → 71.0%; **end-to-end not improved**: 52.2% vs 58.7% for the same 0.5B model without the adapter |
| Inference, HF dev server on M4 (not vLLM) | TTFT 229 ms, 19.3 tok/s at c=1; no throughput gain at c=4 (no batching) |
| API load test, /retrieve, 200 requests at c=8 | 13.2 req/s, 0 errors (p50 1 ms is cache hits; p95 1.8 s) |

**What these numbers say:**
- Retrieval is the big win (10.9% → 63–70%).
- Agents match, but do not beat, the best single-shot RAG on this benchmark.
- The RL router does not beat a fixed "search once, then answer" pipeline (see below).
- SFT taught the agent protocol but did not improve answers (see Limitations).

**About the RL result.** The REINFORCE router reaches the heuristic router's accuracy (67.4% vs 67.4% on 46
questions) with 1.00 vs 2.70 tool calls and 9.2 s vs 19.6 s p50 latency. But it does this by collapsing to a
single `search_documents` call on every question: `required_tool_recall` is 0.0 in
`benchmarks/results/agent_learned/summary.json`, so it never uses the table, SQL, or vision tools. On this
benchmark one good hybrid + rerank search is usually enough, and the tool-cost penalty (`lambda_tool_cost` in
`configs/rl/reinforce.yaml`) makes extra calls unprofitable. The fixed `agent_single_search` baseline (one search,
then the writer, no learning) confirms this: it is correct on exactly the same 46 questions as the learned router
(paired accuracy difference 0.0, bootstrap 95% CI [0.0, 0.0]; 42 of 46 answers are textually identical), at 8.6 s
p50. So the learned policy is equivalent to that fixed pipeline here. Testing whether RL can learn *when* extra
tools pay off needs a benchmark with many more table, arithmetic, and figure questions (roadmap).

Full tables with 95% bootstrap CIs and a per-question-type breakdown: [`docs/experiments/results.md`](docs/experiments/results.md).
Reproduce with `make benchmark`. One question is 2.2 points of accuracy, so read differences against the CIs.

## Architecture

```
PDF / MD / TXT ─► ingestion ─┬─ text layer ─► sentence chunking (page-bounded, overlap) ─┐
                             ├─ ruled tables ─► markdown chunks + SQLite rows             ├─► bge embeddings → FAISS | Qdrant
                             └─ figures ─► caption-anchored PNG crops + caption chunks ───┘   + hand-written BM25 postings

question ─► FastAPI ─► LangGraph agent
                        planner ─► router ─► act ─► critic ─► (router … | writer) ─► cited report
                                     │        │
                                     │        ├─ search_documents : BM25 + dense → RRF → cross-encoder rerank
                                     │        ├─ lookup_table / query_sql : SQLite over extracted tables
                                     │        ├─ analyze_image : VLM over figure crops
                                     │        ├─ run_python : sandboxed arithmetic (LLM writes code)
                                     │        └─ search_web : Wikipedia / Tavily (off by default)
                                     └─ policy: heuristic | LLM (JSON actions) | learned (RL)

every run ─► trajectory JSONL ─► quality filter ─► SFT (LoRA / QLoRA) ─► adapter (hf_local, or vLLM --enable-lora [configured, not validated])
                               └► RL env built on the same nodes and tools ─► router policy (REINFORCE) / LLM router (GRPO)

serving: sync + async jobs (memory | Redis queue + workers), SSE progress, trace ids, Prometheus, rate limiting
deploy : Docker Compose (api, workers, redis, qdrant, vLLM) · Kubernetes (HPA, KEDA workers, GPU vLLM, ingress) [configured, not validated]
```

The "why" behind every component, with alternatives and tradeoffs, is in **[ARCHITECTURE.md](ARCHITECTURE.md)**.
Design notes: [RAG](docs/design/rag.md) · [post-training](docs/design/post_training.md) ·
[agentic RL](docs/design/agentic_rl.md) · [serving](docs/design/serving.md) · [evaluation](docs/design/evaluation.md).
Milestones: [ROADMAP.md](ROADMAP.md).

## Quick start

Requirements: Python 3.11+, [uv](https://docs.astral.sh/uv/), about 6 GB of disk for models. A GPU is optional
(CUDA or Apple MPS are used when present).

```bash
make setup      # venv + dependencies (train, vision, dev extras)
make data       # downloads 4 public arXiv papers (v1) and builds + verifies the benchmark
make ingest     # atlas ingest data/raw  → 4 docs → 426 text / 12 table / 37 figure chunks
make test       # offline test suite (no model downloads)
```

First run downloads the models from the Hugging Face Hub: Qwen2.5-1.5B-Instruct, bge-small-en-v1.5,
ms-marco-MiniLM-L-6-v2, and SmolVLM-256M-Instruct.

### Ask (single-shot RAG)

```bash
python -m atlas ask "What is self-attention?"
```
Real output (abridged). Answer, then evidence with document, page, section, retriever, and score:
```
Answer (Qwen/Qwen2.5-1.5B-Instruct):
Self-attention, also known as intra-attention, is an attention mechanism ... relating different positions of a
single sequence ... [1] ...

Retrieved evidence:
  [1] arxiv_1706.03762.pdf, p.2 score=9.5273 via=hybrid-rrf+cross_encoder section='2 Background'
  [2] arxiv_1706.03762.pdf, p.6 score=4.9797 via=hybrid-rrf+cross_encoder section='4 Why Self-Attention'
  ...
latency: retrieval 596 ms, generation 9792 ms; tokens: 825 in / 167 out
```

### Research (multi-step agent)

```bash
python -m atlas research "By how many BLEU points does Transformer (big) outperform the ConvS2S Ensemble on EN-DE?"
python -m atlas research "..." --policy llm       # LLM router
python -m atlas research "..." --policy learned   # RL-trained router
```
It prints the plan, every router decision and tool call (arguments, latency, new evidence), critic verdicts, and a
report with cited sources. The trajectory is appended to `data/trajectories/trajectories.jsonl`. Unedited runs of
the demo scenario (text, table + compute, figure, multi-hop) are in
[`docs/experiments/demo_output.md`](docs/experiments/demo_output.md) (`python scripts/demo.py`).

### Serve (API + UI)

```bash
python -m atlas serve --port 8000      # UI at http://localhost:8000, OpenAPI docs at /docs
curl -s localhost:8000/ask -H 'content-type: application/json' -d '{"question":"What is BM25?"}'
curl -s localhost:8000/research -H 'content-type: application/json' -d '{"query":"What does Figure 1 of the RAG paper show?"}'
# → 202 {"job_id": ..., "events_url": "/research/<id>/events"}   (Server-Sent Events progress)
curl -N localhost:8000/research/<id>/events
```

### Use a different model provider

```bash
ATLAS__LLM__PROVIDER=openai_compatible ATLAS__LLM__BASE_URL=http://gpu-host:8000/v1 ATLAS__LLM__MODEL=Qwen/Qwen2.5-7B-Instruct python -m atlas ask "..."   # vLLM — configured, not validated
ATLAS__LLM__PROVIDER=anthropic ATLAS__LLM__MODEL=claude-haiku-4-5 ANTHROPIC_API_KEY=... python -m atlas ask "..."
ATLAS__LLM__PROVIDER=extractive python -m atlas ask "..."   # no LLM: extractive baseline, fully offline
```

## Design summary

**RAG.** Chunks are sentence-packed to about 1000 characters with 150 characters of overlap and never cross
pages, so each chunk has one exact page citation. Retrieval is hybrid: BM25 catches exact tokens (model names,
numbers), dense retrieval catches paraphrase. RRF fuses the two by rank, which avoids score-scale mismatch. A
cross-encoder reranks the top 30. The prompt numbers evidence `[n]`, and the papers' own bibliography brackets
are rewritten to `(ref n)` so the model cannot confuse them with our citations. Invalid markers are detected.

**Agent.** A LangGraph cycle of planner → router → act → critic, which then loops or hands off to the writer. The
router picks from a fixed action space, so heuristic, LLM, and RL policies are interchangeable and comparable.
Budgets (iterations, tool calls, wall clock), duplicate-call memory, and fallbacks prevent runaway loops.
Failures are recorded, not fatal.

**Multimodal.** Content goes to the cheapest correct extractor. Text comes from the text layer. Ruled tables go
to SQLite, so arithmetic is exact. Figure crops are located via their captions (this works for vector charts), and
a VLM is called only when a question needs pixels.

**Post-training.** The agent's own successful, citation-valid trajectories become SFT data: router steps are
rebuilt with the exact evidence prefix, plus writer examples. Training uses LoRA on a small Qwen model, with a QLoRA
path for 7B-class models on CUDA (configured, not validated). Evaluation compares action accuracy on held-out trajectories.

**Agentic RL.** The MDP's transitions *are* the production node functions, so a trained policy runs unchanged in
the agent. The reward is task success + citation precision + potential-shaped evidence recall − tool cost − steps.
The router is trained with REINFORCE plus a learned baseline. A GRPO path exists for LLM routers.

**Serving.** Research runs are async jobs (202 + SSE) backed by an in-process queue or by Redis plus workers
(idempotency keys, at-least-once delivery, bounded retries, graceful shutdown). Caching covers retrieval,
temperature-0 LLM calls, and embeddings. vLLM would sit behind the same OpenAI-compatible client (configured, not validated; locally an HF dev server stands in). Every request carries a
trace id, and spans cover nodes, tools, retrieval, and LLM calls.

**Distributed.** API replicas scale on CPU (HPA). Workers scale on queue depth (KEDA), because they mostly wait on
inference. vLLM runs one GPU per replica, with prefix caching and multi-LoRA. Qdrant serves shared vector search.
The ingress handles rate limiting and SSE timeouts. All of this is configured, not validated (no GPU/cluster available); manifests are only statically checked.

## Evaluation methodology

* **Benchmark**: `data/benchmarks/atlas_papers_v1.jsonl`, 46 questions over *Attention Is All You Need*, BERT,
  RAG (Lewis et al.), and *Scaling Laws for Neural Language Models*. By type: 28 text, 8 table, 4 compute,
  4 figure, 2 multi-hop. Each question has a gold answer and aliases, and numeric questions have a tolerance.
  Gold evidence is recorded as (file, pages, quote), and `scripts/build_benchmark.py` checks every quote against
  the actual PDF page before writing the file.
* **Retrieval**: Recall@K, Precision@K, MRR, and nDCG@K, with page-level relevance where each gold unit is
  credited once.
* **Answers**: numeric match within tolerance, or boundary-aware containment of the gold answer or an alias, plus
  token F1.
* **Groundedness**: share of answer sentences whose content words appear in the evidence. This is a *lexical
  proxy*, not an NLI judgment.
* **Citations**: validity (markers point to real evidence), precision (cited evidence is on a gold page), and
  coverage.
* **Agent**: success, completion, tool calls, failed / unproductive / duplicate calls, replans, policy fallbacks,
  and required-tool recall.
* **System**: p50/p95 latency, tokens per query, cost (0 for self-hosted), API load test, and inference
  TTFT and tokens/s.
* **Controlled ablations**: each `configs/experiments/*.yaml` overrides only the variable under test. Same
  model, prompts, and benchmark.

```bash
make benchmark-retrieval          # 6 retrieval variants, ~1 min
make benchmark                    # + base LLM / extractive / vanilla / hybrid / hybrid+rerank RAG
make benchmark-agent              # agent policies; also writes evaluated trajectories
python scripts/run_benchmark.py configs/experiments/agent_learned.yaml
make results                      # regenerate docs/experiments/results.md
```

and `atlas worker` processes.

## Limitations

* The benchmark is small (46 questions, one domain). Most ablation differences fall inside the CIs.
* The generator is a local 1.5B model. Several errors are misread numbers even when the right evidence was
  retrieved, which is why better retrieval does not always improve end-to-end accuracy.
* Groundedness is a lexical proxy. Answer matching is containment-based, so a verbose answer that contains the
  gold span counts as correct.
* Table detection handles ruled tables only. The local 256M VLM reads charts poorly; use a 7B or hosted VLM.
* RL uses an extractive writer inside rollouts and a small train/test split. The learned router mainly learned
  *when to stop*, not when to use table or figure tools.
* LLM routers rarely decide to stop. The 1.5B router chose `answer` itself in 3 of 46 runs; the rest ended at the
  tool budget.
* SFT imitated those trajectories and trained on router examples only (a metadata bug dropped writer examples;
  fixed and regression-tested). It improved protocol-following but lowered end-to-end accuracy versus its
  0.5B base. Next: filter out budget-forced steps and re-collect data with writer examples.
* Multimodal tools help only marginally here: table questions 37.5% → 50% with the table tools; compute questions
  0% for all agents. The demo output (`docs/experiments/demo_output.md`) is unedited and includes wrong answers.
* vLLM, real Redis, Docker images, Kubernetes, QLoRA, and full GRPO runs were not executed here (no NVIDIA GPU,
  Docker daemon, or cluster). See IMPLEMENTATION_STATUS.md.
